# 2026-10-05 定量保持器设计方案（与用户确认稿）

## 用户口述的现有语义（已确认，非 bug）

> 「保持器里面每一种资源它的数量应该和标定的数量是一样的，当然这个一样有个前提，就是说网络中的确有这么多。
> 如果没有的话那就不算。假如说网络中只有 5 个泥土但我标定了 10 个泥土，那么实际上那一个保持器里面就只有 5 个泥土。」

> 「实际上它只是相当于一个代理的作用……它所持有的这一片内存跟网络中是共享的。
> 就比如说网络中有 200 个泥土，他标定了 100 个，然后我一直在使用泥土……
> 因为我网络中的泥土数量超过 100，相当于每漏一个它又可以再补上一个，此时它一直是显示 100 的。
> 当我网络中只剩下不超过 100 个的时候，那么此时它的数量也要小于 100。」

**结论**：显示量 = `min(标定量, 网络中该资源的实际存量)`。保持器**不预留、不搬移、不独占**，
它只是把「网络存量」按标定量截断显示。因此：

- 网络 ≥ 标定 ⇒ 恒显示标定量（用掉一个立刻又有网络存量补上）
- 网络 < 标定 ⇒ 显示网络存量（跟着往下掉）
- **不存在「标 65 却少 1」的独立 bug** —— 那是「网络确实只有 64」的正常表现。

验收方式：看快照 `keepers[].counted[]`（2026-10-05 新增字段），它把「保持器算出来的数」直接摊出来，
与 RS 网络自报的存量并列，一次就能判定是「网络真的只有 64」还是「算错了」。

## 设计问题 ①：多个保持器标定同一种资源、标定量不同

### 目标
1. 结果**确定**（同一份存档每次都一样，不依赖遍历顺序）
2. 玩家**能预测**（看一眼就知道谁会赢）
3. 不引入新的界面概念（不发明「优先级数字」这类玩家要学的东西）

### 方案：**取最大值 + 坐标稳定排序**（推荐）

| 情形 | 行为 |
| ---- | ---- |
| 多个保持器标同一资源，标定量 64 / 100 / 325 | 以 **325** 为准（最大的那个标定量是「谁都不想低于」的下限） |
| 标定量相同 | 按**方块坐标升序**取第一个，行为完全确定 |
| 自动合成开关 | **任一**保持器开启 ⇒ 该资源按最大值补货（否则关了的那台会把开着的那台按死） |
| 过量销毁开关 | **任一**保持器开启 ⇒ 按最大值销毁过量（见问题 ② 的例外规则） |

### 为什么取最大值而不是最小值

- 取最小值时，标 325 的那台永远不达标 ⇒ 它会一直请求自动合成 ⇒ **网络被撑到 325 也不停**，
  而且玩家看到两台都在「缺料」，却不知道听谁的。
- 取最大值时，标 64 的那台自然满足（325 ≥ 64），标 325 的那台也能达标，
  **没有人处于「永远差一点」的状态** —— 这与玩家写多个标定量的直觉一致：
  「我都标了，就按最多的来」。

### 为什么按坐标排序而不是「最近放置」/「界面顺序」

坐标是持久化数据，不随区块加载顺序、不随玩家操作历史变化 ⇒ 同一存档每次结果一致。
界面顺序依赖网络图遍历顺序，NeoForge 不保证稳定 ⇒ 会出现「有时取 64、有时取 325」的抖动。

## 设计问题 ②：多个保持器 + 同时开启过量销毁

### 规则（在方案 ① 之上加一条）

**过量判定只按「最大值」执行一次；其余保持器在过量销毁这件事上完全让位。**

```
有效标定 = max(各保持器的标定量)
是否销毁 = 有效标定已满足 且 网络中存量 > 有效标定 且 至少一台开启了过量销毁
```

### 举例（网络里有 400 个泥土）

| 保持器 | 标定 | 过量销毁 | 结果 |
| ------ | ---- | -------- | ---- |
| A | 64 | 开 | 有效标定 = 325（来自 C）；400 > 325 ⇒ 销毁 75，剩 325 |
| B | 100 | 关 | 满足（325 ≥ 100），不参与销毁 |
| C | 325 | 关 | 达标，不销毁 |

上例里 **A 开了销毁、C 没开**，按「任一开启即生效」执行 ⇒ 网络被削到 325。
这条是刻意的：**销毁是「清理过剩」的安全阀，不该因为另一台没开就整体失效**；
反过来若要求「全部开启才生效」，玩家会遇到「我明明开了一台怎么不销毁」。

### 明确不做的事

- **不做「按保持器各自标定量分别销毁」**：那意味着 A 达标就削到 325、C 达标就…… 同一种资源
  只有一个网络存量，无法同时满足两个不同的上限。硬做只会变成「谁先跑谁赢」的竞态。
- **不做「优先级数字」**：玩家要理解 `优先级` 与 `标定量` 两个独立维度，认知成本过高，
  且与 RS 原版的优先级语义（存储优先级）冲突。

## 实现落点（下一轮）

| 项 | 位置 |
| -- | ---- |
| 同资源多保持器聚合 | `KeeperCluster`（已存在：`yieldedResources` / 节点集合），加一个「按资源聚合有效标定」的只读方法 |
| 有效标定 = 最大值 | 新增 `effectiveTarget(resource)`，稳定排序用 `BlockPos.asLong()` |
| 过量销毁的让位 | `KeeperOverflow` / `QuantityKeeperBlockEntity` 的 `destroyAllowed` 判定改为问聚合结果，而不是只看自己 |
| 诊断可见化 | 快照 `keepers[]` 增 `effectiveTarget`，把「谁定的这个数」也写出来（避免玩家再来问） |

**注意**：以上都只改「判定用哪个数」，不改任何搬运 / 合成 / 销毁的**执行**路径，
因此不会引入新的守恒风险。
