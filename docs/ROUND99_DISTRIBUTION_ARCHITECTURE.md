## 0. 结论摘要

**诊断（一句话）**：问题不在「配置项太多」，而在于**「这一件该去哪个工位」从来没有被表达成一个数据**。
判定层只有 (配方, 步序, 物品) 三种身份；目的地只由**总线朝向哪一格**这条物理事实决定；中间那张「分配表」**不存在**。
于是"不误分"只能靠一串**逐点断言**兜住，而断言今天只覆盖了物品类别里的一小块。

**三条最硬的证据**

1. **目的地 = 物理朝向，不是数据**：`MIXE:487 rscc$supplyTargetPos()` = 本总线朝向那一面的相邻方块；
   全仓没有任何"这条总线服务哪个工位/哪一步"的落盘字段（总线 NBT 只有类别 id + explicit 位 + 两个开关，见第 1 节）。
2. **"类别"在传输层会退化成"物品"**：输入类别的导出过滤项是裸 `new ItemResource(item)`（`SEQ:7209`）；
   步骤专用投入物同样（`SEQ:7137`）；只有中间产物带步序组件（`SEQ:7204 ItemResource.ofItemStack(info.filterPrototype())`）。
   ⇒ `input:create:track#minecraft:iron_nugget` 与 `input:create:precision_mechanism#minecraft:iron_nugget`
   在搬运层是**同一个东西**，配方身份在 `transfer` 那一刻已经丢了。
3. **逐工位断言只对"步骤专用投入物"生效**：`EXP:540` 整段包在 `if (chamber.isInputMaterial(item))` 里，
   而 `SEQ:2339 inputMaterialWantedNow(target,item)` 的第 4 行就是 `if (!isStepExtraInput(item)) return true;`（`SEQ:2348`，`Item` 版在 `SEQ:2687`）。
   主原料 / 流体 / 过渡件**没有**逐工位断言，它们的"该不该推"只按**链级**问（`SEQ:15674 isNextForMyMachines`、`SEQ:15855 busExportAcceptsForPush`）。

**推荐方案：B（半自动绑定）**——把"总线 → 工位"这条**已经物理存在**的隐式绑定显式化，
让「默认勾选」与「推料断言」都改为**由工位推导**；玩家的手动勾选降级成覆盖项，而不是必须项。理由与分阶段见第 5 节。

**本轮可落地的最小改动（3 处，都不改玩家既有勾选语义）**

1. 默认导出集从「全输入 + 全中间产物」（`SEQ:2198 defaultExportCategoryIds`）改成
   「**本总线朝向工位**能处理的那一子集」（机器类型 × 本链 `ownedSteps`；判不出才退回全选）。
2. 把 `EXP:566` 那一处只对步骤专用投入物的逐工位断言，扩成一个对**所有**推料物品生效的唯一实现
   `stationAcceptsPush(target, stack)`，并在 `transferItem` 最前面调用。
3. `fillInternalForBus` 的目标量合并键从 `Item`（`SEQ:9675 itemTargets.merge(..., Math::max)`）改成
   「类别 id + 物品」，避免两条总线抢同一份缓冲时互相覆盖（第 7.4 展开）。

**需要用户拍板的三件事**：默认集改变会让老存档里"从未配置过"的总线表现变化；能否接受"总线不再各自勾类别"；见第 8.2 节。

## 2. 现状架构：谁决定「这一件该去哪个工位」

### 2.1 数据流（文字图）

```
                    ┌──────────────── 判定层（唯一事实源，全在 SEQ 上）────────────────┐
                    │ ownedSteps()         本仓负责哪些 (配方,步序)                     │
                    │ chainOwnedSteps()    整条链合起来能做哪些 (配方,步序)             │
                    │ computeBusCategories() → 类别表（input/fluid/intermediate/result/scrap）│
                    │ chainBusOwners()     类别 id → 勾了它的输出总线坐标（升序）        │
                    │ machineReservedRecipe() 共机的多条配方谁先占                      │
                    └───────────────┬───────────────────────────────────────────────────┘
   RS 网络 ──(fillInternalForBus, SEQ:9563)──▶ 执行仓内部存储（整条链一个池）
                                                    │
                                                    │  (EXP, 被 MIXE 替换掉 RS 原版策略)
                                                    │  取料源 = 池；按"类别"过滤 = 裸物品 / 带步序原型
                                                    ▼
                                    输出总线（每条一根，只能朝一个方向）
                                                    │  rscc$supplyTargetPos()
                                                    ▼
                                    总线朝向的那一格 = 机器 / 置物台
                    ┌──────────────────────────────────────────────────────────────┐
                    │ 推料断言（EXP:540 起）：只对"步骤专用投入物"逐工位判          │
                    │ 其它：链级 isNextForMyMachines / busExportAcceptsForPush      │
                    └──────────────────────────────────────────────────────────────┘
   机器 / 置物台 ──(IMP, 收回侧)──▶ 回网络（全自动：非输入类恒收回；输入类受保护）
```

### 2.2 三个"身份"与它们的事实源（这张表就是问题的核心）

| 身份 | 由什么表达 | 事实源 | 缺口 |
| --- | --- | --- | --- |
| **物品身份** | `ItemResource(item)` | 物品注册名 | 抽取层只按 `Item` 匹配（`EXP:791 inSlot.is(prototype.getItem())`），组件不参与 |
| **步序身份** | `create:sequenced_assembly` 数据组件 | 件自己带着（`GUARD:310 judgeStep`） | **原料 / 成品 / 废料没有步序**；`create:unprocessed_obsidian_sheet` 这类中间件也没有（`SEQ:15709` 直接 `return true`） |
| **目的地身份** | 方块朝向 | `MIXE:487` | **不落盘、不显示、不校验** |

### 2.3 单一事实源清单（判定问题 → 唯一实现）

| 问的问题 | 唯一实现 | 位置 |
| --- | --- | --- |
| 这一件现在走到第几步、下一步归谁 | `SequenceMaterialGuard.judgeStep` / `StepVerdict` | `GUARD:264-310` |
| 本仓负责哪些 (配方, 步序) | `ownedSteps()` | `SEQ:16016`（实现在 `SEQ:16047`） |
| 本链合起来能做哪些 (配方, 步序) | `chainOwnedSteps()` | `SEQ:15995` |
| 本链此刻还要不要这一件 | `isNextForMyMachines` | `SEQ:15674` |
| 这一轮该不该把这类别交给这条总线 | `categoryExportFilters` | `SEQ:7027` |
| 哪几条总线勾了这个类别（共享/份额） | `chainBusOwners` → `busCategoryOwners` | `SEQ:6627` / `SEQ:287` |
| 这一轮几条总线同时开工（份额） | `exportShare` | `SEQ:7246` |
| 共用的机器先归哪条配方 | `machineReservedRecipe` | `SEQ:7600` |
| **这个工位这一步要不要这件**（仅步骤专用投入物） | `inputMaterialWantedNow(BlockPos,Item)` | `SEQ:2339` |
| 这个工位压着在制件吗 | `unitInFlightAt` | `SEQ:3054` |
| 这条总线的目的地 | `rscc$supplyTargetPos()` | `MIXE:487` |

**结论**：11 个判定点里，**没有一个回答"这件货物该去哪个工位"**；只有两个回答"这个工位要不要它"，
其中一个只对步骤专用投入物表态（`SEQ:2348` 早退），另一个只回答"忙不忙"（`unitInFlightAt`）。

### 2.4 各类在链路里扮演的角色

| 类 | 实际角色 | 不负责 |
| --- | --- | --- |
| `RsccBusCategory`（`CAT`，466 行） | 一个类别的 **S2C 快照 + 稳定 id 规则 + 候选集合**（`input:<配方>#<物品>` `CAT:120/430`、`intermediate:<配方>:<步序>` `CAT:296`、`result:`/`scrap:`/`fluid:`、只喂标签页的 `recipe:` `CAT:169`） | 不决定谁该拿：它只描述类别本身；判定层复用的仅是它的**前缀判定**（`CAT:210 isInput` / `CAT:224 isIntermediate`），而只喂标签页的 `recipe:` 类别明确不进任何判定（`CAT:153-167`） |
| `RsccBusConfig`（`CFG`，134 行） | **剪贴板载荷**：复制/粘贴一条总线的配置（过滤槽 + 类别 + explicit + 自动收回 + 强制普通） | 与分配无关；它是"配置同步"的防腐层 |
| `RsccBusInterference`（`INTF`，236 行） | **总线 → 执行仓的归属判定**：线缆簇够到 ≥2 条不同的链 ⇒ 归属未确定 ⇒ 停用延长型（`INTF:107`） | 解决的是"这条总线归哪台仓"，**不是**"这件货归哪个工位" |
| `BusCategoryConfigScreen`（`SCR`，2948 行） | 两级 UI：配方标签页 + 六节（原料→输入时原料→流体→成品→废料→中间产物） | 纯展示 + 勾选，判定全在服务端 |
| `ImporterScreenMixin` / `ExporterScreenMixin` | 各加一颗"执行器模式"排 + tooltip（`ExporterScreenMixin:67`、`ImporterScreenMixin:84`） | 不参与任何判定 |

## 3. 冲突分类学（每条：触发 / 证据 / 后果 / 现缓解）

> 后果四档：**丢料**（资源消失或永久冻结）、**多推**（多开件 / 重复消耗）、**卡死**（产线永久停）、**仅界面**（不影响搬运）。
> 「已修」列只标代码里**存在**的缓解，不等于实机验证过。

### A 类：架构必然（换配置、换玩家也躲不掉）

## 5. 三个候选架构

### 5.1 定义

- **A 全自动推导**：由执行仓单一事实源**反向驱动**总线。总线不再有独立类别配置，只当"一根管子"；
  执行仓按"每个工位当前该吃什么"直接决定往哪条总线投什么。
- **B 半自动绑定**：总线**绑定到工位/机器**（这条绑定今天已经由朝向物理存在，只需显式化）；
  类别由绑定推导（机器能做哪些步）+ 少量覆盖（同类别多工位、跨链等少数场景）；推料按工位断言。
- **C 全手动标记框架**：新增一套"标记"系统，玩家给每条总线/每个工位打标记，类别与目的地都由标记决定。

### 5.2 五维对比

| 维度 | A 全自动推导 | **B 半自动绑定（推荐）** | C 全手动标记 |
| --- | --- | --- | --- |
| 玩家配置成本 | **最低**（理论上零配置） | **低**：默认零配置；只有"同类别多工位"等少数场景需要一次覆盖 | **最高**：每条总线/每个工位都要标；用户已明确否决（"太麻烦"） |
| 错误率 | **中**：推导错了没有任何人工纠错入口（只能拆机器） | **最低**：推导正确 ⇒ 零操作；推导不出（空工位、多变体）⇒ 保守不推 + 可覆盖 | **中偏高**：标记本身会标错；标错后系统"照错执行"且看起来很确定 |
| 实现代价 | **最高**：要动 `ownedSteps` 属主语义（有前科：`SEQ:16079` 记录的"第 20 轮严重回归"就是把它链级展开/显示集混进属主），且 `FACE` 模式、脱绑委托、多条链全要重算 | **中**：改动集中在三处（默认集、逐工位断言、目标量合并键），**不动属主/名额/份额** | **中高**：新增一套持久化标记 + 全部 UI + 兼容层，且它**不解决** C 类问题（按物品判定的那部分） |
| 老存档兼容 | 差：总线配置直接失效（玩家的勾选无处安放） | **好**：配置位全部保留；`explicit == false` 的总线才吃新默认集（可加"一次性迁移提示"） | 差：需要迁移/补标记，否则所有旧墙都停摆 |
| 新类 bug 风险 | **高**：反驱动一旦判错，全链停摆且无手动出路 | **中低**：新增的是"更严格的闸门 + 更聪明的默认值"，判不出时退回今天的行为 | **高**：标记与真实世界（方块被拆/换）不同步 ⇒ 幽灵标记、错标 |

### 5.3 推荐：**B**，三条硬理由

1. **事实已经存在，只差"说出口"**：`rscc$supplyTargetPos()`（`MIXE:487`）已经能回答"这条总线服务哪一格"；
   `ownedSteps()` + `recipeTypeId`（`SequencedRecipeProbe:93`）已经能回答"这个工位能处理哪些步"；
   `PATT:368 UnitEntry.machinePos` 甚至已经有玩家在流程编排里一次性标好的「步 → 机器」。
   B 只是把这三份已有事实**接起来**，不发明新概念。
2. **它同时压掉 A、C 两类最贵的后果**：A1（万能总线）由"默认集按工位推导"解决；
   C1/A5（按物品判定的往返）由"逐工位断言扩到全部物品"解决；而**不动**属主语义 ⇒ 不触发第 20 轮那类回归。
3. **它给了"玩家零配置也正确"的路，同时保留手动纠错**：这正是用户两条要求的交集——不想手动标记，但要求不误分。

## 6. 直接回答用户那两句

### 6.1 「是否所有输入输出总线都需要玩家手动标记？」

**不需要，而且现在也不该走这条路。** 理由：决定"去哪里"的信息**已经有三份自动来源**，只是没被用起来：

1. **朝向**：总线朝向哪一格，就已经是"它只能服务这一台机器/置物台"（`MIXE:487`）。这是玩家摆方块时**已经做过的一次标记**。
2. **机器类型**：每个工位能做什么由方块决定（Create 的 pressing/filling/deploying…），
   与配方每一步的 `recipeTypeId`（`SequencedRecipeProbe:93`）可直接比对 ⇒ "这台机器能不能做这一步"是可判的。
3. **在制件**：台上那件过渡件自带 `(配方, 步序)`（`GUARD:310`）⇒ "这个工位此刻轮到哪一步"是可判的（`SEQ:4777 pendingStepOn`）。

所以"零手动标记"在**大部分布局**下成立；需要玩家**一次性**（不是每条总线）交代的只有两类：
① 同一条链上**两台同型号机器**都空闲、且都能做同一批步 —— 这时"给哪台"不影响正确性（可以按坐标稳定选一台，`SEQ:7246` 已经在做）；
② 玩家**故意**让一条总线跨用途（例如一条总线同时给两台不同类型的机器供料）—— 这是非标准布局，B 方案里它需要一个"覆盖"勾选。

### 6.2 「如果不手动标记，怎么保证不误分？」

落到具体机制，一共 5 条，今天**只有后 2 条真正生效**（这就是缺口的精确位置）：

| 机制 | 回答什么 | 今天存在吗 | 位置 |
| --- | --- | --- | --- |
| M1 目的地 = 朝向（物理事实，玩家已标记） | 这条总线**只能**去这一格 | ✅ | `MIXE:487` |
| M2 工位"能做什么" = 机器类型 vs 步的 `recipeType` | 这一步**允不允许**在这台机器上做 | ⚠️ 只用于 `ownedSteps` 的推断（`SEQ:16070`），**不用于推料闸门** | `SEQ:16047` |
| M3 工位"此刻该做什么" = 台上的在制件 `(配方, 步序)` | 这一件**是不是**这一步 | ✅ 有实现 | `SEQ:4777 pendingStepOn` / `SEQ:3054 unitInFlightAt` |
| M4 逐工位断言：这一件**必须是**该工位当前步的投入物 | 推**错**就放弃（"推错 = 绝不发生"） | ⚠️ **只对步骤专用投入物**生效（`SEQ:2348` 早退） | `EXP:566` → `SEQ:2339` |
| M5 共机排队 + 份额 | 多台/多配方**不要同时**开工 | ✅ | `SEQ:7600` / `SEQ:7246` |

**⇒ 保证不误分的欠账只有两条**：
- **M2 没接进推料闸门**（B-1：用它决定"默认勾什么"）；
- **M4 覆盖面太窄**（B-2：扩到所有会被推的物品/流体）。

补齐后，"误分"的判定链变成：**朝向 → 机器类型能不能做这一步 → 台上那件是不是这一步 → 这一件是不是这一步的投入物**，
四道全部是**只读、可判、判不出就保守不推**（保守的代价是暂时不喂，不是喂错）。
这与用户"推错 = 绝不发生"的硬要求一致：**任何一道判不出，就不推**。

## 7. 专项核查：「类别详细配置」能否在同一台机器的多条配方之间正确区分？

### 7.1 能区分的那一层：界面与勾选（✅）

- 输入类别带**配方段**：`input:<配方id>#<物品>`（`SEQ:5001`，`CAT:449 inputRecipeId`）——
  「精密构件的铁粒」与「列车轨道的铁粒」在界面/勾选里**是两个类别**（这正是 2026-10-05 那次修复的意义）。
- 中间产物带**配方 + 步序**：`intermediate:<配方id>:<步序>`（`CAT:296`）——
  两条配方的同一步序互不覆盖（`CAT:255-261` 记录了旧 id 造成"另一条配方的过渡件永远导不出去"）。
- 界面按配方分页（`SCR` 两级结构，页名 = 配方结果物名）+ 页内六节 ⇒ **同一台机器的多条配方各有各的页**。

### 7.2 不能区分的那一层：传输 / 池 / 目标量（❌）

| 环节 | 为什么分不开 | 证据 |
| --- | --- | --- |
| 导出过滤项 | 输入类别的过滤项是裸 `ItemResource(item)`，**配方段不进过滤项** | `SEQ:7209` |
| 抽料 | 从共享池按**物品**匹配（连组件都比不了） | `EXP:649 inSlot.is(item.item())`、`EXP:791` |
| 备料目标量 | 按 `Item` 合并取 max ⇒ 两条配方抢一份缓冲 | `SEQ:9675` |
| 步序（输入类） | `input:` 类别**没有步序** ⇒ 同一配方多步用同一物品（track 第 0/1 步）**只有一份** | `CAT:120` + `SEQ:5001` |
| 判定兜底 | 唯一的配方级校验是"候选不带步序 ⇒ 物品相同即放行"（`SEQ:15815` / `SEQ:15866` 的 `want == null ⇒ return true`） | `EXP:672` → `SEQ:15855` |

**结论**：**"多条配方"在配置层能区分，在搬运层区分不了**；而且"同一配方的多个步共用一个物品"连配置层都区分不了（C1）。
所以现状的正确说法不是"类别详细配置没用"，而是：**它是一份"意图声明"，而执行层只按"物品"兑现**——
这正是用户感觉"我明明勾了却还是乱"的机制来源。

### 7.3 最小修复点（只给建议，不改代码）

按"代价 / 收益"排序，**前两条与第 5 节 B-1/B-2 是同一件事**：

1. **把输入类别补上步序上下文（收益最高，代价中）**
   `inputCategoryIdForRecipe`（`SEQ:5001`）增加可选步序 → `input:<配方>#<步序>#<物品>`；
   `CAT` 增加 `inputStep()`，解析规则与 `intermediateStep()`（`CAT:237`）同源（取最后一段），
   旧 id `input:<配方>#<物品>` 继续认（`inputStep() == -1`，行为逐字不变）。
   ⇒ 同一配方多步同物品（track 0/1）才第一次可以分别勾选、分别断言。
2. **推料加逐工位断言并让断言读配方/步序（收益最高，代价低）**
   新增 `stationAcceptsPush(target, stack)`：`pendingStepOn(target)` 给出 (配方, 步)，
   该步的投入物集合（`SequencedRecipeProbe.assemblyStepInputs`，与 `SEQ:2339` 同源）**必须包含**这一件；
   过渡件则要求"件自身步序 == 该工位当前步 + 1"。
   在 `EXP:524 transferItem` 的最前面调用（今天只有 `isInputMaterial` 分支里有）。
3. **目标量按 "类别 id + 物品" 合并（收益中，代价低）**
   `SEQ:9675` 的 `Math::max` 在"不同配方段引用同一物品"时改为 sum，再按 `BUS_ITEM_TARGET_MAX` 夹；
   同一类别的重复引用仍取 max。（否则两倍需求永远只备一倍。）
