# 齿轮堵塞 / 多余中间产物 —— 实机实验协议（照着做即可取证）

> **这份文档回答一个问题**：你要在游戏里做哪些操作，才能让我（下一位接手）**仅凭日志**定位
> 「齿轮堵塞」「多余中间产物」「序列装配各种异常」，而不需要反复来回问。
>
> 结论先给：**6 个段落、约 25 分钟**。每一段都在制造一种**已知的失败模式**，
> 因此日志里"有没有异常"与"异常长什么样"都会有直接对照。
>
> 跑完只需两条命令（我会拿到所有证据）：
> ```
> python tools\analyze_blockage_experiment.py      # 齿轮 / 在制品 / 序列装配的证据与判定
> python tools\verify_single_unit_supply.py        # 供料不变式与修复后行为
> ```

## 0. 开始之前（3 步，顺序不能反）

```
① powershell -ExecutionPolicy Bypass -File tools\manual_compile.ps1
     → 期望 `===== COMPILE OK (324 sources) =====`
     （这一步会刷新构建指纹与 .class 时间戳，是后面「实判定」的唯一基准）

② 关掉游戏，重新启动（必须晚于第 ① 步；不关就还是旧 JVM，日志只能当基线）

③ 进入存档后，在聊天栏输入：
     /rs_create_compat assemblydebug on
     /rs_create_compat shortagemode suspend
     /rs_create_compat diag
   `assemblydebug on`      → 确认诊断开着（默认就是开，打一次留个凭据）
   `shortagemode suspend`  → 缺料处置＝挂起（这是默认档；注意命令是 **shortagemode**，不是 shortage）
   `diag`                  → 立刻落一份快照（它包含每个执行仓的**当前存量、在制、五量**，
                             是所有"多余中间产物"结论的基线）
```

**启动后请先确认这一行**（没有它，后面的日志无法自证是哪一版代码）：

```powershell

```

## 1. 六个段落（每段都有明确的"制造什么故障"）

> 时间栏里的数字是**最短观察时长**。短于它，慢重试窗口（10 秒/工位）与 5 秒聚合都还没出现第二个周期。

| 段 | 操作 | 制造什么 | 最短时长 |
| -- | ---- | -------- | -------- |
| **A** | 在线缆外的合成终端下单 **精密构件 x1**，什么也不动，让它跑完 | 正常基线（应当全程无阻塞） | 3 分钟 |
| **B** | 再下单 **精密构件 x64** | 长跑稳态（在制品并发、缓存堆积最容易在这里暴露） | 5 分钟 |
| **C** | 下单 **精密构件 x1**，然后在产线还在跑时：<br>① 打开**自动合成监视器**，点该任务的「**挂起**」<br>② 等 30 秒<br>③ 点「**继续**」 | 挂起冻结 + 恢复（挂起期间任何搬运都该停） | 2 分钟 |
| **D** | **不用手动放东西**（2026-10-05 更正）：直接下单 **精密构件 x1**，反复做若干次 —— 装配有概率失败，失败时废料（例如小齿轮）会自己留在置物台上。看到横幅「下游拒收」后**先别动手**，观察执行舱是否在几秒内把那一件收回网络（这是新加的堵塞自愈） | **齿轮 / 废料堵塞本体**（用户实机就是这个形态，不是人为摆出来的） | 5 分钟 |
| **E** | 保持 D 的现场不变，把缺料处置切成「一直等待」：<br>`/rs_create_compat shortagemode wait`<br>然后再下单 **精密构件 x1** | 对照：等待档下卡住闸门应当**永久失效**（设计内） | 3 分钟 |

| **F** | 把缺料处置切回 `/rs_create_compat shortagemode suspend`，然后下单 **列车轨道 x1**，让它跑完 | 候选组回归（"铁粒 **或** 锌粒"是否真的进了 RS 样板） | 3 分钟 |

**D 段的具体做法（2026-10-05 更正：不需要人为摆件）**：

> 我上一版写的「用创造栏拿一个小齿轮放到置物台上」是**误解**。你实机遇到的是
> **装配失败时自己留下的废料**（小齿轮）压在置物台上。因此 D 段不需要任何手动操作：

1. 下单 **精密构件 x1**，让它跑；
2. 装配失败留下废料时，输出总线会把「同一件」推不出去 ⇒ 日志出现
   `push_stalled reason=DESTINATION_REFUSED`，横幅提示下游拒收；
3. **先别拿走**，等几秒：新加的「堵塞自愈」应当把那一件收回网络，并打一条
   `unblock_recovered {item=…} from=(x,y,z) reason=target_held_item_blocking_next_push`；
4. 如果十几秒后它**仍然**压在置物台上（日志里没有 `unblock_recovered`），
   那就是自愈没生效 —— 把日志与快照发回，这条日志本身就是定位入口。

> ⚠️ **别在 D 段手动破坏方块 / 拆机器** —— 那会产生大量无关事件，把关键证据淹掉。
> 要停就点监视器的「挂起」。

## 4. 怎么读那三条命令的输出

> `analyze_blockage_experiment.py` 的 `--scenario` 既接受**段号**（`--scenario 4`）
> 也接受**产物名**（`--scenario 精密构件`）。注意两者含义不同：段号是"这一份日志里的第几段"，
> 产物名会命中**所有**该产物的段落 —— 想把 A/B/D 三段放在一起对比时用产物名更方便。
> 另外：**没有推送 / 卡住事件的段会被自动跳过**（没跑到产线的那种），因此报告里的段号可能不连续。

### `analyze_blockage_experiment.py`

它按 `binding task=` 把日志**切成订单段**，然后对每一段给 6 条断言：

| 断言 | 它在问什么 | FAIL 意味着 |
| ---- | ---------- | ----------- |
| ① | 5 秒窗口内有没有把**同一件重复推给同一工位** | 重复推送 = **多开一件在制件**的直接机制 |
| ② | 在制过渡件「产出 − 完成」是否 ≤ 订单量的 4 倍 | 超出 = 有在制件永远走不完 / 在仓里堆积 |
| ③ | 同一 (件,工位) 的 `waited=` 是**单档**还是**多档** | 多档 = 粘住后每 10 秒故意再放行一次（**齿轮堵塞本体**） |
| ③b | 有没有 `waited > 200` | 有 = 该工位已被放行 ≥3 次，齿轮被反复重推 |
| ④ | 任务结束回收的残留里有没有**过渡件** | 有 = 过渡件被当成废料收回了（不该发生） |
| ⑤ | 该订单的成品有没有入网 | 无 = 这一段根本没跑到终点（任务没完成） |

**示例（2026-10-04 08:28 的旧日志，只作格式示例，不是本次实验）**：

```
段 2：精密构件 x1（task=57e041f0，序列 3 步）
  实测：推送事件 1 条 / 卡住 555 条 / 过渡件产出 4 / 过渡件完成 0 / 成品入网 0
  FAIL ③ 同一 (件,工位) 的 waited 只有单档
       stuck 条目 555｜item:create:cogwheel @(-7,-58,5) → 66..544 共 437 档，步长 1
                        item:create:large_cogwheel @(-7,-58,6) → 66..390 共 55 档，步长 6
                        item:create:large_cogwheel @(-7,-60,6) → 72..462 共 63 档，步长 18
  FAIL ③b 没有 (件,工位) 的 waited 超过 200 tick
       超过 200 的: [('create:cogwheel', '(-7,-58,5)', 544), ('create:large_cogwheel', '(-7,-60,6)', 462), …]
  FAIL ② 在制过渡件「产出 − 完成」≤ 订单量的 4 倍
       产出 4 / 完成 0 / 差值 4 ⇒ 有 4 件在制件没走完
```

这三条 FAIL 就是「齿轮堵塞 ⇒ 多余中间产物」的**完整证据链**：
`cogwheel` 在 `(-7,-58,5)` 被反复放行重推（waited 一路涨到 544），
同时 `incomplete_precision_mechanism` 产出 4 件、一件都没走完。

## 5. 常见问题

**Q：我能不能只跑 D 段（齿轮堵塞）？**
A：能，但建议至少连 A（基线）一起跑 —— 没有基线，就无法区分"这一段的异常是堵塞造成的"
还是"这台机器本来就一直这样"。A + D 大约 8 分钟。

**Q：`shortagemode wait` 是干什么的？为什么 E 段要切它？**
A：它是「缺料时一直等，不要自动收回」的档位。切到它之后，卡住闸门会**永久失效**
（这是设计内行为，由 W2 等待豁免覆盖）—— E 段就是为了把这个"设计内"用日志记下来，
免得下次有人把它当成新 bug 再查一遍。跑完记得切回 `/rs_create_compat shortagemode suspend`。
（完整命令表见 `TECHNICAL_HANDOFF.md` §3.7。）

**Q：我一定要手动放一个"小齿轮"制造堵塞吗？会不会弄坏存档？**
A：不会。那只是一个物品放在置物台上，拿走即可。若你不想手动放，也可以**用别的产线占住同一台机械手**
（例如同时下单列车轨道，让机械手忙在另一条线上）—— 效果等价，日志里的证据形态也一样。
实在不想制造故障，就只跑 A / B / F 三段，我可以给出"没有复现"的结论 ——
但那样**无法**验证堵塞修复是否生效。

**Q：`[rscc-ledger]` 一条都没有，是不是没在记？**
A：不是。账本**对平时刻意零输出**，只有失衡才会说话。所以"没有 ledger 行"就是"没有失衡"
—— 这正与本轮修复前"没有 logger ⇒ 永远没有告警"完全不同。要确认它在工作，
可以在跑完 D 段后看 `run\logs\latest.log` 里有没有 `[rscc-ledger] unbalanced` 的 **WARN** 行。

**Q：实验会不会让日志爆掉？**
A：不会。三族新增日志都带节流：`[rscc-build]` 每进程 1 行；`[rscc-ledger]` 对平零输出、
失衡时每 30 秒最多 1 条；`[rscc-dedupe]` 5 秒合并。稳态最坏速率仍与"机器数量"线性相关、与 tick 无关。
