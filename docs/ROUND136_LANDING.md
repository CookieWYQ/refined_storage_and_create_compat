## 2. 根因：三条回收路径全部到不了它（判据自身的死锁）

| 路径 | 为什么不行 |
|---|---|
| `reclaimRuntimeStationResidue` 的「进度卡死」/「裸过渡件」 | 两条都要求**该格 `machine_full` 计数 > 0**（强旁证）。名额为 0 时本仓**根本不再尝试推送** ⇒ 永远收不到新的 `machine_full` ⇒ 旁证永远不成立。**这是判据自身的死锁**：它要的证据只有「继续推」才产生，而名额 0 恰好禁止推。 |
| 「结果池物品」分支 | 要求台上那件属于配方结果池。金板是**起步原料**，不是结果池物品。 |
| 判据 ④「`登记物品 == 台上物品` ⇒ 合法等待，绝不碰」 | 方向正确（防「刚推上去就被抢回来」），但**没有时间上限** ⇒ 一件永远不会被机器接手的裸原料被这句话永久保护。 |

补充：这不属于「区块没加载」或「会话太长」，只取决于「哪一格先咬住一件永远不动的裸原料」，
所以表现成「部分工位永久不恢复、看起来随机」——与用户历次描述一致。

## 3. 修法 A：超龄裸件的守恒回收（`staleBareUnitRecoverable` + 新分支）

### 判据（可证死，不是「等得久」）

Create 的序列装配在一步**真正开始**那一刻就会把置物台上那件**原地替换**成带
`create:sequenced_assembly` 进度组件的过渡件（`SequencedAssemblyRecipe#advance`）。因此：

1. 台上恰好 1 件、**不带进度组件**（外层既有判据 ②③）；
2. 物品与**本仓登记的那一件完全一致**（唯一凭据：本仓确实往这一格推过这件东西）；
3. 该登记 `step < 0`（起步原料 / 步骤专用投入物；过渡件登记一律不在这条分支动）；
4. 物品是**起步原料或步骤专用投入物**，且**不是**本仓过渡件（双重保险）；
5. 自**本仓上一次向这一格成功推送**（`InFlightUnit.sinceTick`，每次成功推料都会刷新）起
   已满 `STALE_BARE_UNIT_TICKS = 1200` tick（**60 秒**）。

⇒ 这 60 秒里没有任何机器接手过它（接手必然写入进度组件），也没有任何一次成功推料刷新它
（活着 / 刚喂过的工位永远不会满足第 5 条）。60 秒远超任何正常起件节奏（Create 一步是秒级，
见既有 `RUNTIME_RESIDUE_PROGRESS_STALL_TICKS = 200` 的取值依据）。

### 动作（复用既有守恒通道，不新增搬运实现）

`SIMULATE 夹量 → 精确抽 1 件 → 优先进网络（`StorageNetworkComponent#insert`）→ 网络装不下才收本仓
（`acceptTransitionLocally`）→ 两侧都装不下就原样还回站台`，随后才删该工位的在制登记 / 死件标记 /
拒收证据，并**逐笔记守恒账**（`flowLedger.fromMachine` + `flowLedger.toNetwork` 同额）。
`moved <= 0`（一个字节都没搬走）时**不改任何登记**，下一轮再判。

### 为什么不会「多占一份料 / 多开一件」（用户第 134 轮驳回过的口径）

收回的那一份**回到网络**，名额恢复后本仓重新开件时**从网络取回的就是同一份**：
物品守恒账两侧同额，总件数不变；`capacity = remaining − inFlight` 里 `inFlight` 由登记表算，
登记撤掉后名额回到 2，任务只会补开**本来就还欠着的 2 件**，不会多开。

### 有界性

- 节拍：每 `RUNTIME_RESIDUE_SWEEP_INTERVAL_TICKS = 40` tick（2 秒）一轮；
- 数量：每轮至多清 1 件（`RUNTIME_RESIDUE_CLEAR_MAX = 1`）；
- 范围：只遍历 `inFlightUnits`（本仓真的成功推过料的工位，通常 1~4 个），每轮 ≤16 格；
- 冷却：新增 `STALE_BARE_RECOVER_COOLDOWN_TICKS = 6000`（**5 分钟**）/工位。
  为什么要比既有的 10 秒长得多：这类工位是「机器根本不吃这件料」（机械手没拿步骤投入物 / 没通电），
  修好之前收回网络的那一份会被同一条总线**再推回同一格**；5 分钟让一次性故障第一次就自愈，
  真坏掉的工位只留低频、物品守恒的重试，不放大成每秒推收往返。

## 4. 修法 B：孤儿登记清理（东西早就不在台上的那种）

`dropOrphanBareRegistration`：同一超龄条件下（`step < 0` / 非过渡件 / 满 60 秒），若**该格非空**但
`stationHoldsPipelineResidue(station, unit)` 判定「整工位都找不到本仓登记的那一件、也找不到本产线过渡件」
⇒ 这条登记已失去凭据：**只删本模组账本，一个字节都不动**（台上不是我们的东西，绝不碰），名额随之自愈。
判不出来（未加载 / 抛异常）一律不动（宁可不删，不丢凭据）。
与修法 A 恰好互补：A 管「东西还在、只是永远不动」，B 管「东西早就没了 / 被换成无关物」。

## 5. 「选择」按钮：本轮仍未修（如实写明）

用户本轮补充：「整块都没有了，就是应该是点不到的」「不稳定出现，只遇到过几次」。
我这一轮能确认的事实（源码级）：

- 「总样板」那一行只属于 `SequencePatternTerminalScreen`（全工程只有它用 `pattern_slots` 语言键）；
- 该界面在「总样板 / 单元样板」这一排**只有一个真正的 Button 控件**（`generateButton` = 生成样板），
  它在 `init()` 里**每帧重建、无条件创建、从未被移除**，只有 `active` 灰化，不会消失；
  该排其余控件是 4 条滚动条（`SptScrollbarWidget`）与单元样板槽（`renderBg` 手绘，逐帧必画）；
- 因此用户看到的「整块消失且点不到」**不可能**是这个按钮被条件跳过 —— 我还没找到能解释它的路径。

**还差的一项信息**：下次复现时截一张图，或直接说是「生成样板」那颗、还是「单元样板翻页滚动条」、
还是另一颗（例如某个子界面里的「确定 / 取消」）。有这一项我可以直接定位；现在盲改只会引入新的回归。
（这条与精度构件那条不同：那条有快照现场可证死，这条没有任何可复现的现场。）

## 9. 已知边界（如实写明）

- 只处理 `step < 0` 的**裸起步原料 / 步骤专用投入物**；带进度组件的卡死件与裸过渡件仍走既有判据
  （仍需 `machine_full` 强旁证）—— 本轮没有放宽那两条，避免把「正在加工」的件误抢；
- 网络与本仓都装不下时**不回收**（保留登记），不会为了解死锁而丢物品；
- 「收回网络后又被同一条总线推回同一格」在机器真坏时会低频循环（每 5 分钟一次），这是刻意保留的
  「低频重试」而不是静默；
- 未做实机验证：本轮只有快照证据 + 编译 + 自检 + 构建/部署回读，**没有**在真实存档里看到那两条
  `residue_cleared` 日志（需要用户重启后按 §8 对）。
