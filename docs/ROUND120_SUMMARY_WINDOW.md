## 2. 旧行为（根因，两条独立的机制）

1. **轮转完全没有考虑「玩家正在看/正在点」**：`broadcastChanges` 的暂停条件只有
   `getCarried().isEmpty()`。玩家「看一秒再点」不产生任何包，服务端无从得知，
   于是轮转照做；点击包到达服务端时服务端早已轮转，而客户端还在画旧映射
   （客户端显示永远落后服务端一个**单程延迟**）⇒ 点到的槽号被服务端按**新映射**解释 ⇒ 取到相邻样板。
   *（顺带确认：原版 1.21.1 `ServerGamePacketListenerImpl#handleContainerClick` 对
   `stateId` 落后**只做一次 `broadcastFullState()` 纠正、并不拒绝点击**，
   所以这个错位不会被原版挡住 —— 这也是复核报告结论正确的直接证据。）*
2. **一次点击内可能用到两份映射**：`removeItem` / `setItem` 都当场 `rebuildWindow()`。
   压缩表是「非空槽」的列表，拿走一格后整表**前移一位**，于是同一格立刻显示成相邻样板；
   「取出来又放回去」两次点击之间压缩表已变 ⇒ 放回去和相邻那张**交换**，
   样板落到同一台仓的另一个槽（不丢，但步序/槽位对应关系变了）。

## 3. 新行为

### 3.1 轮转闸门收敛成一个纯函数 `shouldAdvanceRow(...)`

```java
if (slotCount <= ROW_COLS || !carriedEmpty) return false;                 // ① 不比 4 格多 / 手上拿东西
if (lastClickTick >= 0 && now - lastClickTick < INTERACT_QUIET_TICKS) return false;  // ② 刚被点过
return !isRotateSettling(now, lastRotateTick);                            // ③ 上一次轮转还没出安全窗
```

- `INTERACT_QUIET_TICKS = 8`（400 ms）：`clicked()` 在本行窗口格上记 `rowLastClickTick[row]`；
  最近 8 tick 内被点过的行**先不轮转**。玩家连续操作时该行**完全停转**（不是"转得慢"），
  一停手 0.4 s 后自动恢复。
- 顺带修正：只有**真实样板张数 > 4** 才轮转（旧实现 `> 1`：2 张样板也会每秒来回晃）。

### 3.2 「轮转后安全窗」：这段窗口内的点击**不执行**（本轮的核心闸）

`ROTATE_SETTLE_TICKS = 4`（200 ms）。一行刚轮转完的 4 tick 内，该行窗口格上的点击：

1. 记交互时间戳；
2. **不执行** `super.clicked(...)`（`ClickType.QUICK_CRAFT` 还要 `resetQuickCraft()` 复位拖拽中间态）；
3. 置 `pendingFullResync`，下一次 `broadcastChanges()` 改走 `broadcastFullState()`
   —— 内容 + 光标一次性推真值给客户端，客户端立刻看到真实状态。

**取舍（为什么不是「按轮转前的映射执行」）**：点击包跨在轮转那一拍两端时，服务端**无法区分**
玩家看到的是轮转前还是轮转后的内容；按哪一份执行都有一半是错的。
两害相权：**忽略一次点击**（紧随一次全量重同步、玩家立刻看到真值、可以再点）
远好于**换给玩家另一张样板**。这是本轮唯一的可见代价：极少数情况下**点一下没反应**。

### 3.3 一次点击只用一份映射快照

`clicked()` 里 `beginClickSnapshot()` 拷贝 `rowStart / rowSlotCount / rowSlotMap`（逐行 `arraycopy`），
`finally` 里 `endClickSnapshot()` 复位；`clickDepth` 处理嵌套（`clicked` → 原版内部 `quickMoveStack`）。
点击期间 `mapToUnitSlot` 一律读快照 ⇒ **「取用」与「写回」永远指向同一张样板**
（旧实现 `setItem` 先 `rebuildWindow()` 再按新映射写）。

### 3.4 「洞」：拿空的那一格在本轮转周期内**保留空位**

`removeItem` 把某槽拿空时记进 `rowHoles[row]`（`BitSet`）；`rebuildWindow` 把「洞」当作压缩表里的
**一个空位条目**（位置按真实槽下标升序，其它条目一个都不动）⇒

- 拿走一格，其它格**不位移**；
- 「放回去」自然落回**原槽**（不再是和相邻那张交换）；
- 洞的生命周期 = 一个轮转周期：**该行下一次轮转 / 换页 / 该行换了执行仓**时清空
  （不会永久留一个空位）。

### 3.5 顺带修掉的显示 bug（同一条映射链路上）

旧 `mapToUnitSlot` 用 `floorMod(start + col, count)`：样板不足 4 张时会出现
「1 张样板 4 格全显示同一张 / 2 张样板两两重复」。而 `WindowContainer.setItem` 里
「空格子 ⇒ 放进第一个空样板槽」那条分支本来就是按「不足 4 张 ⇒ 有空位」写的。
现在 `windowIndex(start, col, count)` 在 `col >= count` 时返回 `-1`（空位），两处口径一致。

**客户端界面没有改**：外观一个像素都没动，也没有新增控件、没有改包协议
（`client/screen/ChamberUnitsSummaryScreen.java` 的 diff 为空；界面只是照常接收槽位同步）。

## 4. 选型理由

复核报告给了 A/B/C 三个方案，本轮选 **A（最小修改）+ 安全窗**：

| 方案 | 为什么不选 |
| --- | --- |
| A 纯「有交互就暂停」 | **单独不够**：首次「看一秒再点」不产生任何前置包，服务端没有信号；必须叠加安全窗才能保证不错样板 |
| B「把 `rowStart` 随 S2C 下发 + 锁定一个 tick」 | 需要**改包协议**（新字段/新包）并两端同改，超出本轮最小改动边界；而且「锁定一个 tick」同样只是把不确定窗口挪个位置 |
| C「取消自动轮转，改手动翻页」 | 会**去掉一个既有特性**（>4 张样板时其余样板将无法从本界面取用），属产品行为变更，需单独拍板 |

所以：**A 的「安静期」+「安全窗（宁可不响应）+ 一次点击一份映射 + 洞」**，
既不改协议也不删特性，且把「点错样板」这条最难受的路径封死。

`ROTATE_SETTLE_TICKS = 4` 的依据：安全窗要覆盖「轮转发生 → 客户端收到 → 玩家点 → 包回到服务端」
这段时间里**客户端仍画旧映射**的那一段。客户端画旧映射 ⇒ 点击生成时刻 < 轮转 + 单程延迟；
包到达时刻 < 轮转 + 2 × 单程延迟。取单程 ≤ 2 tick（RTT ≤ 200 ms，正常联机）⇒ 窗口 ≤ 4 tick。

## 6. 未验证清单（诚实边界）

1. **完全没有实机验证**：没启动游戏、没点过界面、没改包联网、没读 `latest.log`。
   所有结论来自源码 + 行为模型；「玩家多久撞一次」没有数据。
2. **残余风险**：单程延迟 > 2 tick（RTT > 200 ms）时，「轮转后安全窗」仍可能不够长，
   理论上的错样板窗口 = `2 × 单程延迟 − 4 tick`（自检 ②-4b 只证明「安全窗内绝不错」，
   不能证明「任何网络都不错」）。彻底消除需要**协议层回执**（方案 B 的强化版），本轮未做。
3. **「点一下没反应」的实际观感未验证**：安全窗内被丢弃的点击会以「内容瞬间弹回」呈现，
   理论上玩家再点一次即可；但**是否会被误认为"卡了"** 需要实机看。
4. **洞的观感**：拿走一张后那一格留空到下一次轮转（≤ 1 s）；连续拿走多张会留下多个空位。
   如果实机觉得"空位碍眼"，可把洞改成「只保留最近 1 个」或「缩到 2 tick」，需再拍板。
5. **旧档里同格多张样板**（`stacksTo(64)`）在窗口格里点击仍是「一格一张」的 `Slot` 语义，
   `removeItem` 可能只拿走一部分 ⇒ 该槽不会变空 ⇒ 不留洞（本轮行为正确但观感未验证）。
6. **`quickMoveStack` 的 Shift 点击**在安全窗内也被 `clicked` 一并拦下（不在 `quickMoveStack` 里
   单独拦；原版所有 Shift 点击都经 `clicked` 进入），这一点未实机确认。
7. 本轮**未审计**同一套「滑动窗口」范式在其它界面（例如单元样板管理舱的分组列表）里的同类问题；
   若以后出现「滑动列表点错项」，可按本轮同一套「交互时间戳 + 安全窗 + 快照」处理。
